# Record of processing: client personal data in the hub

This record lists every store on the hub's data disk that holds personal data about a client, what it holds, why, on which legal basis, how long it is kept and which processors touch it. The registry in `lib/personal-data.js` is the source: `GET /api/admin/system/personal-data-stores` (Superadmin) prints the same list with the retention texts as the code has them. A test (`scripts/personal-data-writers.test.mjs`) fails when a new data file is written through one of the hub's JSON write helpers (`writeDataJson`, `writeHotJson`, `updateJsonLocked`, `writeJsonAtomic`, `writeTextAtomic`, `createJsonOnce`) without being registered here or listed as holding no client personal data. Files written with plain file-system calls (append-only logs, uploaded files, media) are not seen by that test; they are registered by hand, as the rows below show.

Asoldi serves businesses. The personal data is that of the people at a client business (contact person, staff in photos, people in meetings) and of leads.

## Switches

Every part below that writes new data or deletes data is behind a switch in `automation-settings.json` (Superadmin, Automatisering). All are off by default. With every switch off, three Superadmin routes still answer, read only: the registry, the export and the purge status (`GET /api/admin/system/personal-data-stores`, `GET /api/admin/sales/:id/personal-data-export`, `GET /api/admin/system/retention-purge`). An unlink still deletes an archived transcript copy made while the archive was on, and the Fireflies store skips recordings an erase removed; with no copy and no erase these do nothing.

| Switch | Off (default) | On |
|---|---|---|
| `privacy.archive.enabled` | Linking a recording writes nothing new; an unlink still deletes a copy archived earlier. | A copy of the transcript is archived on link and deleted on unlink. |
| `privacy.purge.enabled` | No purge runs; the erase route answers 403. | The daily purge runs; the erase route works (a dry run unless `dryRun: false`). |
| `privacy.purge.mode` | `shadow`: the purge writes only a would-purge report. | `auto`: expired items are deleted. |
| `media.signedUrls.enabled` | The media routes answer 404 `{code:'disabled'}`. | The media manifest and its 24-hour signed download links work. |
| `media.rightsConfirm.enabled` | The portal shows no rights checkbox. | Each upload records "Vi har rett til å bruke disse bildene". |
| `fireflies.candidateRanker.enabled` | No candidates are shown. | Unlinked recordings show ranked client candidates; a person links with one click. The ranker never links. |
| `fireflies.autoLink.enabled` | Nothing links on its own beyond the booked Meet room. | A recording links only when an attendee e-mail equals one client's contact e-mail and a slot the hub booked for that client starts within 30 minutes. |

## Data-subject requests

- **Export.** `GET /api/admin/sales/:id/personal-data-export` (Superadmin) returns one JSON file with every registered store's records and files for the client. Each file is listed with its size and a sha256; files over 32 MB (meeting video, call audio) are listed with an empty sha256 and are not read, so an export never loads large media into memory. The client portal profile in the export is the client's own business's: a portal user with several businesses is never matched by user id alone.
- **Erase.** `POST /api/admin/sales/:id/erase` (Superadmin) answers 403 while `privacy.purge.enabled` is off. It is a dry run unless the body says `dryRun: false`; the dry run lists, per store, what would be deleted, redacted, held or retained. A client with a running contract is erased only with `allowActiveContract: true` (409 otherwise). An id with no client card is erased only with `allowMissingClient: true` (404 `{code:'client-not-found'}` otherwise): without the card the stores cannot see what the client had, and every sent offer is then held as a possible signed contract. The erase:
  - deletes the client card, unsigned offers, recordings, the transcript archive, briefs, the media manifest, attachments, the imported site copy, the developer handoff, call recordings and their cache entries, workshop needs, developer requests, SEO client data, the planned-recording sessions of the client and the boot contact corrections about the client (in the file and in the list the running hub loaded, which the admin action that applies them uses), and removes the booked meeting from Google Calendar. When the calendar delete does not happen (safe mode, an error), the event is reported as retained, and the result and the delivery audit name its calendar and event ids, so a person can remove it by hand;
  - deletes portal uploads file by file: the files the client's own card or business profile links to, and unlinked files of a portal user who is in this business only. A file another business or card also links to, and an unlinked file of a portal user who also belongs to another business, are held (`shared-portal-user`) and listed; files only another business links to are left out;
  - holds a portal business another client card is also on (`shared-business`): a card with the same portal business, the card the business profile names as its website build, a card whose own profile is this business's, or a card of the business's portal user that names no other business. Then every file the business profile links to and every unlinked file of its portal users is held and listed, and so is the business's entry in `media-rights.json` (in the file and in its copies); only a file this client's own card alone links to is deleted;
  - holds what another client card also points at, with the reason in the result: a recording on another card (`shared-recording`), a call recording or a recording cache entry that another card's lead id, call id or phone number also finds (`shared-recording`), and a boot contact correction that also matches another card (`boot-correction`, named by its place in the file);
  - puts every erased recording id on the erased list (`privacy/erased-meetings.json`, ids only) before it deletes the recording, so the next list page, fetch, webhook or hydration from Fireflies does not store it again, and a media copy that was running when the erase happened removes what it wrote and records nothing. A recording's media folder is found by the name the media copy gives it, never by joining the id on the card to a path;
  - takes the client out of the snapshot copies and automatic backups of the stores it deletes from or redacts: client cards, offers, portal offers, Fireflies meetings, inbox items, workshop needs, developer requests, media rights (except the entry of a business another card is on), the call recording cache and the boot contact corrections; the SEO client file's own backups are deleted. A copy that does not parse is not rewritten: it is listed under `kept` and rotates out with the other copies;
  - blanks the client's e-mail items (sender, subject, text) and keeps their ids;
  - keeps signed contracts, the sent offer of a signed client, accepted portal offers, the client portal account and the hub site (bookkeeping law, the client's own account, the running site), in the stores and in their copies;
  - holds library files tagged `client:<id>` and lists them, so they are removed in the media library once it is checked where asoldi.com uses them;
  - keeps ids-only logs, which are dropped by month;
  - records the erase in the delivery audit with ids only.

## Retention purge

`lib/delivery-retention.js` exports the delivery loop step `retention-purge` (daily). It asks every store with a purge rule for its expired items, using `retention.*`: in `shadow` mode it writes only a report under `privacy/purge-reports/` (ids and paths), in `auto` mode it deletes the items and reports what went. Every run, shadow or auto, also writes `privacy/retention-state.json` (the time of the last run, the mode and the report name; no client data), which keeps the step to once a day. The transcript archive's date is recomputed from the client as it is when the purge runs (signing, a decline or the contract end move it). A lead's last activity comes from stamps only real activity sets (creation, meetings, recordings, calls, a sent contract, a decline, nurture mail), never from the card's last change, so automatic passes do not push the date forward. Nothing is purged while the sales store reads as empty. `GET /api/admin/system/retention-purge` shows the last run; `POST /api/admin/system/retention-purge/run` runs it once (403 while the switch is off).

## Transcript archive

With `privacy.archive.enabled` on, every link of a recording with talk (webhook, pull, paste, admin link, backfill) writes `transcript-archive/<client>/<sha256>.json`, once per transcript text; a newer copy of the same meeting replaces the older one. An unlink or a move deletes the copy from the client it left, also after the switch has been turned off, so a copy made while it was on never stays with the wrong client. Nothing is archived for a client whose retention date has passed, so the sync never writes back what the purge removed. `node scripts/backfill-transcript-archive.mjs` lists the recordings on cards that have no archived copy (a dry run); `--apply` writes them, and is refused while `privacy.archive.enabled` is off.

## Client media

With `media.signedUrls.enabled` on, the media manifest lists the client's files: Kundedata media, logos and product images, e-mail attachments and library files tagged `client:<id>`. A Kundedata link to a portal upload is listed only when the uploader is one of the client's own portal users (the linked user, the profile's owner or an active member of the client's business). With `media.rightsConfirm.enabled` on, the portal stores the rights answer for the uploader's own files that exist, in one write per request (at most 50 files, at most 1000 answers per client); answers for files that are gone are dropped on the next write.

## Recording candidates

With `fireflies.candidateRanker.enabled` on, recordings that are on no card and whose Meet room no client booked show up to five ranked client candidates in the unlinked recordings list (Tilbud), with a purpose pick (`sales`, `workshop`, `iteration`, `demo`). Nothing is linked until a person clicks; that link is the person's link and later automatic passes keep it. Signals: attendee e-mail equals the contact e-mail (+50), attendee domain equals the website domain and is not free mail (+30), within 3 hours of a slot the hub booked (+30), business name in the title (+20), the contact among the speakers (+15), client marked not sold (−20). The link audit (`fireflies-link-audit/`) holds ids only. `scripts/eval/fireflies-rank.mjs <labels.json>` measures top-1 accuracy on a labelled set kept outside this repository.
